Smart Personal Memory System ? implementation report

Milestone 3, Feature 3. Implemented September 10, 2026. This feature builds on the existing authentication, conversation history, document knowledge, AI provider, task, and reminder systems. Existing unrelated workspace changes were preserved.

1. **Feature overview.** LifeAdmin can suggest and remember preferences, personal facts, working context, and important decisions across conversations. Both Ask LifeAdmin and document chat offer Save memory / Ignore suggestions, saved-memory feedback, Forget this, and a memory-count indicator. Settings ? Memory supports viewing, search, paging, editing, individual deletion, complete deletion, and disabling memory. Confirmation is the default; automatic saving is an explicit opt-in limited to simple answer-length preferences.

2. **Architecture changes.** The existing AI service performs bounded memory extraction from the latest user message, with a conservative exact-statement fallback when the provider fails. Extraction never reads assistant output, uploaded document text, or an entire conversation history. A dedicated memory service validates content, signs temporary consent proposals, saves approved memories, ranks relevant memories, and records successful use. Workspace answers, document answers, and existing DOCX drafting receive bounded memory context through their existing generation services. Deterministic task counts, navigation, and reminder answers retain their existing behavior. No new AI provider or dependency was introduced.

3. **Database changes.** Added `memories` with the required userId, type, content, importance, source, confidence, lastUsedAt, createdAt, and updatedAt fields. Internal fields include generation, fingerprint, searchable terms, useCount, and contentUpdatedAt. User/generation/fingerprint is unique; additional user-scoped type and term indexes support listing and retrieval. User gains memorySettings.enabled (default true), autoSavePreferences (default false), generation, and consentVersion. Existing accounts use these defaults without a destructive migration. Confirmed and automatically saved memories persist; pending suggestions do not create MongoDB records. The normal existing chat transcript still stores non-credential user statements.

4. **API changes.** See the API table below. All routes use the existing JWT authentication middleware and derive ownership from the authenticated user. Both chat POST responses gain a transient `memory` object containing suggestions, saved-memory feedback, and an optional availability flag. Existing response fields remain compatible. No chat-history schema was duplicated, and proposal tokens/content are not added to history records.

7. **Security review.** Every memory operation includes the authenticated user and current generation. Suggestions require a signed, user-bound, 15-minute consent token with its own audience and an HMAC-derived signing key separate from login tokens; neither token type can be substituted for the other. Settings changes, edits, and deletion invalidate older consent tokens. Complete deletion advances the user's memory generation before removing old rows, so in-flight extraction cannot revive deleted memory. Saves and retrieval recheck settings before returning, and failed concurrent saves clean only their own insertion. New credential disclosures matching the guard are rejected before chat persistence or provider calls. Memory extraction/save/edit validation rejects sensitive topics, credentials, temporary or hypothetical statements, low-confidence output, unsupported facts, and instruction-like content. AI-extracted content must be an exact span of the user's statement. Personal facts, projects, decisions, PDF preferences, and all preferences outside the narrow automatic-saving allowlist require explicit Save. Memory context is untrusted personalization, not document evidence or authorization to act. No secrets, source messages, or provider diagnostics are logged by the memory feature.

8. **Testing results.** The memory suite passed 47 checks against the local MongoDB with mocked provider output/extraction. It covers suggestions without persistence, acceptance, persistence after clearing chat, ownership, edits, search, disable/re-enable, opt-in autosave, critical-information consent, unrelated messages, sensitive-content rejection, document grounding, individual/all deletion, token separation and replay invalidation, in-flight deletion, preference conflicts, and prompt limits. Authentication, workspace assistant, document chat, document chat quality, document generation, and document knowledge regression suites passed. The production frontend build passed with the existing Vite warning for a JavaScript bundle larger than 500 kB. No interactive browser or live-provider answer-quality test was performed.

9. **Known limitations.** Extraction is deliberately conservative and currently targets English first-person declarations; indirect statements, other languages, complex phrasing, and unusual personal facts can be missed. Sensitive-data detection is heuristic, not a guarantee against arbitrary encoding or deliberately disguised credentials; this feature is not a credential vault. Ignore dismisses a transient proposal and stores nothing; repeating the same statement later can produce another proposal. Unsaved suggestions disappear on reload and expire after 15 minutes. Exact duplicates are deduplicated, while broad semantic duplicates remain editable by the user. Recognized answer-length, report-format, and language conflicts use the latest saved/edited content; other conflicting memories need user review. Retrieval examines at most 100 indexed candidates, sends at most six memories / 2,000 characters, and favors relevant medium/high-importance records. Repeated use increases priority; there is no vector memory search. Saves check a 1,000-memory per-user quota. Disabling retains saved rows for user management but stops extraction/retrieval. Deleting memory does not delete the original chat transcript, past AI answers, or context already sent to a provider; clear chat separately where appropriate. Existing report export remains DOCX?remembering a PDF preference does not add PDF export or authorize pretending a PDF was created. Browser usability and live AI personalization still require manual verification.

| Method and route                       | Behavior                                                                          |
| -------------------------------------- | --------------------------------------------------------------------------------- |
| `GET /api/memories?q=&page=1`          | Own memories, 25 per page; counts and public settings                             |
| `PATCH /api/memories/settings`         | Boolean enabled / autoSavePreferences settings                                    |
| `POST /api/memories/confirm`           | Save a valid signed proposal; body `{ "token": "..." }`                           |
| `PATCH /api/memories/:id`              | Edit own content/type with full validation                                        |
| `DELETE /api/memories/:id`             | Forget one memory and invalidate old suggestions                                  |
| `DELETE /api/memories`                 | Advance generation and delete all saved memories                                  |
| Existing workspace/document chat POSTs | Return transient suggestions or autosave feedback after a successful conversation |

Run the new tests from `server/` with `npm.cmd run test:memory`. Existing MongoDB and JWT settings are sufficient. MongoDB creates indexes automatically in the normal development setup; deployments that disable auto-indexing must create the indexes declared in Memory.js through their usual database migration process. No historical conversations are automatically mined or backfilled.
